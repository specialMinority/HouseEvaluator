# PC 조회 작업자 보안 점검과 보완

점검일: 2026-09-13. 대상은 HouseEvaluator의 공개 Render API와 이 PC의 전용 조회 작업자다. PC 전체의 침해 여부를 판정하는 포렌식이나 제3자 사이트 침투 시험은 아니다.

## 위협과 기존 방어

PC가 Render에 HTTPS로 작업을 가져오는 구조이며 외부 사용자에게 PC의 수신 포트를 공개하지 않는다. 사용자 접속코드는 작업자 인증키와 별개다. 작업 종류는 검색·상세 URL 조회로 제한되고 명령·파일 경로·임의 헤더를 받지 않는다. 출처별 HTTPS 주소·경로 허용 목록, DNS의 공인 IP 검사와 해당 IP로의 연결 고정, 리다이렉트 차단, 응답 크기·시간 제한이 있다. 원문의 JavaScript를 실행하는 브라우저 수집기는 사용하지 않는다.

확인한 주요 위험:

1. 평소 Windows 사용자 권한으로 Python을 실행한다. 파서나 의존 코드가 취약해지면 같은 사용자에게 보이는 파일의 피해 범위가 넓다.
2. 공유 접속코드를 아는 이용자가 반복 조회를 지속할 수 있다. 단일 작업/페이지 제한과 전체 시간별 사용량 제한은 다르다.
3. 응용 코드의 URL 검사만으로는 코드 실행 취약점 발생 후의 내부망 접근까지 제한하지 못한다.
4. 작업자 키 파일에 생성 도구의 계정/그룹 접근 권한이 남아 있어 실제 운영 계정 중심으로 정리할 필요가 있다.

이번 점검에서 직접 원격 명령 실행 경로를 발견한 것은 아니다. 악용 가능성을 수치로 추정하거나 공격이 불가능하다고 보증하지 않는다.

## 보완 단계

- [x] S1 실행 코드·권한·수신 포트·키 파일 권한 점검.
- [x] S2 작업자를 별도 비관리자 컨테이너로 격리. PC 폴더·Docker 제어 소켓을 공유하지 않고 읽기 전용 실행 파일, CPU·메모리·프로세스·로그 제한 적용.
- [x] S3 작업자 네트워크를 끄고 Unix 소켓을 통해 고정 HTTPS 목적지만 연결하는 별도 통신 통로 구성. 목적지 DNS 공인 IP 검사와 고정 연결, 접속·응답량·시간 한도 적용.
- [x] S4 작업자 자체의 시간별/일별 조회 예산과 별도 통신 통로의 요청 총량 제한. 키 파일 접근 권한 축소.
- [x] S5 악성 URL·내부 IP·DNS 변조·리다이렉트·반복 작업·자원/파일/네트워크 격리 회귀, 운영 전환 및 실제 공개 기능 확인.

## 근거

- [OWASP SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html): URL 허용 목록과 DNS/IP 검사를 함께 적용한다.
- [Docker 실행 제한](https://docs.docker.com/engine/containers/run/), [자원 제한](https://docs.docker.com/engine/containers/resource_constraints/): 컨테이너를 만들기만 해서는 자원 상한이 생기지 않는다.
- [Docker Engine 보안](https://docs.docker.com/engine/security/): 권한·호스트 공유 범위를 최소화하며 격리의 잔여 위험을 구분한다.

## 적용 설정과 확인 범위

`compose.worker.yaml`에 모든 제한을 명시한다. 작업자 메모리 384 MiB·CPU 0.5개·64 PID, 통신 통로 128 MiB·CPU 0.25개·32 PID다. 두 실행 파일 시스템은 읽기 전용이며 추가 Linux 권한을 모두 제거하고 권한 상승을 막는다. PC의 문서 폴더와 Docker 제어 소켓을 공유하지 않으며 PC 키 파일 하나만 읽기 전용으로 전달한다. 임시 파일과 컨테이너 로그에도 한도가 있다.

작업자는 `network_mode: none`이며 소켓 볼륨도 읽기 전용이다. 통신 통로는 `houseevaluator-personal.onrender.com`, `suumo.jp`, `www.chintai.net`, `realestate.yahoo.co.jp`의 HTTPS 443만 허용한다. 실제 인증·HTTPS 본문은 작업자와 목적지 사이에서 TLS 암호화하며 통로는 해독하지 않는다. 목적지의 모든 DNS 주소를 검사하고 검증한 공인 IP로 연결한다. 내부·루프백·링크 로컬·멀티캐스트·IPv4 변환/터널 주소는 거절한다. 통로가 없거나 거절하면 직접 연결하지 않는다.

전 이용자를 합산해 검색 12회/시간·URL 조회 30회/시간·합계 120회/24시간으로 제한한다. 통신 통로에는 원문 연결 60회/분·500회/시간·2,000회/일, 제어 서버 60회/분·12,000회/일의 별도 한도가 있다. 사용량은 전용 볼륨에 작업 종류와 시각만 저장한다. 상태 DB 오류·과도한 시계 후퇴 시 조회를 중단한다. 재시작으로 한도가 초기화되지 않는다. 잘못된 인증은 연결 상대별 최대 10회/분이며 정상 인증의 한도와 분리한다. 여러 사람이 같은 프록시를 쓰거나 분산 공격을 하는 경우의 한계는 남는다.

실제 컨테이너에서 비관리자 UID·권한 상승 차단·Linux 추가 권한 없음·PC 폴더/Docker 소켓 미공유·실행/소켓 디렉터리 쓰기 거절·직접 인터넷/내부망 연결 불가·통로의 루프백 목적지 거절을 확인했다. 허용 통로를 통한 Render 상태 조회는 정상 TLS로 HTTP 200을 반환했다. 실제 내부 서버를 스캔하거나 제3자에 악성 요청을 보내지 않았다.

키 파일 3개의 ACL을 실제 운영자·SYSTEM·Administrators로 축소했고 원래 ACL은 Git 제외 경로에 백업했다. 비밀값 자체를 소스·테스트·보고서에 기록하지 않는다.

## 남는 위험과 대응

- **공유 코드·가용성:** 코드를 아는 사람은 정상 조회를 요청할 수 있고 공동 한도를 소진시켜 다른 사람의 조회를 방해할 수 있다. 지금 한도는 PC 자원과 원문 요청량의 상한이다. 이용자가 늘면 개인별 인증·사용량 제한이 필요하다.
- **컨테이너/통로 취약점:** Docker는 가상 PC 전체를 완전히 분리하는 보증이 아니다. 작업자 취약점의 피해 범위를 줄였지만 커널·Docker의 취약점이나 별도 통신 통로 자체의 코드 실행 취약점은 남는다. Windows·Docker Desktop·Python 이미지를 보안 업데이트하고, 이미지 변경 후 제한/기능 검증을 반복한다.
- **동일 Windows 사용자:** 사용자 계정 권한을 이미 가진 악성코드는 키를 읽거나 Docker를 제어할 수 있다. 이번 조치는 이미 감염된 PC를 치료하지 않는다. 키 유출 의심 시 작업자를 중단하고 Render/로컬 전용 키를 함께 교체한다.
- **허용 사이트와 데이터:** 통로는 TLS를 해독하지 않으므로 HTTP 경로 검사는 응용 코드가 담당한다. 허용 호스트나 CDN 자체의 문제까지 배제하지 않으며, 원문 파서의 취약점 위험도 0이 아니다. HTML의 JavaScript를 실행하지 않고 읽기/해석 크기를 제한한다.
- **저장 장치:** 정상 프로그램의 DB·로그·임시 파일은 제한되어 있다. 코드 실행 취약점으로 전용 쓰기 볼륨을 악용하는 경우까지 하드 디스크 쿼터로 보장하지는 않는다. 디스크 여유가 급감하거나 반복 재시작되면 즉시 중단한다.
- **운영 의존성:** PC·로그인·인터넷·Docker Desktop이 필요하다. 절전·로그아웃·원문 정책 변경과 소규모 무료 서비스의 중단 가능성은 남는다.

즉시 중단은 `./scripts/stop_personal_worker.ps1`, 다음 로그인 자동 시작도 막으려면 `Disable-ScheduledTask -TaskName 'HouseEvaluator Public Query Worker'`를 함께 실행한다. 새 시작/중단 방식은 [REMOTE_WORKER.md](REMOTE_WORKER.md)를 따른다. `Stop-ScheduledTask`만으로 실행 중 컨테이너는 중단되지 않는다.
