# Phase 7: 무료 우선 저장소와 데이터 수명 관리

현재 구현은 **단일 인스턴스 + 로컬 SQLite 파일**이다. Python 표준 라이브러리만 사용한다. 데이터 공급 계약, 실제 데이터, 운영 서버 또는 외부 백업 계정을 생성하지 않는다. PostgreSQL/PostGIS, 다중 서버, 복제 및 작업 큐는 실제 물량과 예산이 확인된 이후의 작업이다.

`backend.v2.storage.open_store(target)`가 저장소 진입점이다. 로컬 파일 경로만 지원하며 PostgreSQL URL, 네트워크 공유, SQLite URI, 메모리 저장소를 운영 대상으로 받지 않는다. 지원되지 않는 저장소 URL을 임의로 SQLite 파일명으로 바꾸지 않는다.

## 저장 범위와 기본 보존 정책

- `v2_current`: 공급사별 현재 전체 스냅샷 1개. 새 전체 스냅샷의 검증과 교체는 기존 `SnapshotStore`의 단일 트랜잭션으로 처리한다.
- `v2_receipts`: 공급사·스냅샷 식별자, 시각, 콘텐츠 해시. 원본 관측·주소·가격은 저장하지 않는다. 이미 받아 본 스냅샷이 정리 뒤 재생되어 현재 데이터로 되살아나는 것을 막기 위해 유지한다.
- `v2_maintenance_audit`: 정리 시각, 삭제한 스냅샷·관측·백업 개수, 처리하지 못한 백업 개수만 남긴다. 원본 관측이나 사용자 평가 입력은 기록하지 않는다.
- 현재 스냅샷과 백업의 기본 최대 보존 기간은 **7일이라는 개발 가정**이다. `--retention-days`로 1~365일을 설정할 수 있으나, 실제 계약에서 더 짧게 요구하면 그 기간을 적용한다.
- 백업 만료는 `백업 생성 + 보존 기간`, `가장 오래된 스냅샷 as_of + 보존 기간`, `가장 빠른 데이터 사용권 만료` 중 가장 빠른 시각이다. 백업을 반복해서 만들어도 원본 스냅샷의 보존 기한은 늘어나지 않는다.
- `storage` 허용은 실제 계약에서 백업 저장과 보존 기간까지 포함하는지 운영자가 확인해야 한다. 현재 스키마의 `storage: true`만으로 그러한 계약이 존재한다고 판단할 수 없다. 백업 금지 조건이면 이 기능을 사용하지 않는다.

## 백업

프로젝트 루트에서 실행한다. 라이브 DB는 백업 전용 디렉터리 밖에 있어야 한다.

```powershell
python scripts/maintain_v2_store.py backup --db .runtime/v2.sqlite3 --backup-dir .runtime/backups --retention-days 7 --suppliers .runtime/config/suppliers.json
```

`backup_store(db_path, backup_dir, *, now=None, retention_days=7, revoked_source_ids=())`는 SQLite 온라인 백업 API로 일관된 복사본을 만든다. 동시에 조회하거나 새 스냅샷을 가져와도 복사 결과의 원자성이 유지된다. 복사 후 `integrity_check`, 지원 스키마, 현재 원본 스냅샷의 해시·정규화·권리·보존 기한을 검사한다. 만료되거나 철회된 원본은 새 백업으로 발행하지 않는다. 먼저 정리하고 재시도한다.

검사를 통과하면 고유 이름의 `.sqlite3`와 `.manifest.json`을 발행한다. 매니페스트에는 SHA-256, 크기, 생성·만료 시각, 공급사별 식별자와 관측 개수만 들어간다. 관측 내용이나 자격 증명은 넣지 않는다. 동일 이름 덮어쓰기는 허용하지 않고 매니페스트를 마지막에 발행한다. 발행 도중 실패하면 이 작업에서 만든 임시 파일과 매니페스트 없는 백업을 제거한다. 시스템 전원 차단 등으로 생긴 고아 파일은 자동 삭제 대상으로 추측하지 않는다.

해시는 우발적인 변경·손상 검출용이며, 파일과 매니페스트 모두를 바꿀 수 있는 공격자에 대한 서명이 아니다. 백업 디렉터리는 운영자만 쓸 수 있게 OS 권한으로 관리한다. 로컬 백업과 운영 DB가 같은 디스크에 있으면 디스크 고장 대응은 되지 않는다. 별도 장치 복사는 사용권과 비용을 확인한 뒤 운영자가 구성해야 한다.

## 복구

매니페스트 이름은 백업 명령 출력의 `manifest_file` 값을 사용한다. 아래의 이름은 자리표시자다.

```powershell
python scripts/maintain_v2_store.py restore --manifest .runtime/backups/실제-매니페스트-이름.manifest.json --destination .runtime/restored-v2.sqlite3 --suppliers .runtime/config/suppliers.json
```

`restore_backup(manifest_path, destination, *, now=None, revoked_source_ids=())`는 **아직 존재하지 않는 새 경로**로만 복원한다. 기존 DB나 SQLite sidecar(`-wal`, `-shm`, `-journal`)가 있으면 거절한다. 운영 중인 DB에 덮어쓰기하지 않는다.

매니페스트·해시·크기·만료를 확인하고 임시 복사본에서 스키마와 모든 원본 권리를 다시 검사한다. 공급사 메타데이터가 매니페스트와 일치해야 한다. 복사 전후 원본 해시도 확인한다. 모든 검사를 통과해야 새 목적지로 발행하며, 중간 실패는 원본 DB와 기존 목적지에 영향을 주지 않는다. 복구 뒤에도 기존 `SnapshotStore.read_current()`는 요청 시각의 권리 만료를 검사한다. 복구가 만료 권한을 갱신하지 않는다.

운영 교체는 별도 절차다. 서비스를 중지하고 복원된 새 DB를 확인한 뒤 서버의 DB 경로를 새 파일로 바꾸어 재시작한다. 먼저 기존 경로·설정을 기록하여 되돌릴 수 있게 한다. 이미 권리가 만료·철회된 기존 DB를 되돌리기 대상으로 사용하지 않는다.

## 정리: 기본은 실행 계획

```powershell
python scripts/maintain_v2_store.py cleanup --db .runtime/v2.sqlite3 --backup-dir .runtime/backups --retention-days 7 --suppliers .runtime/config/suppliers.json
```

이 명령은 `status: plan_only`와 대상 개수·이유를 출력하며 DB나 백업을 바꾸지 않는다. 운영자가 실제 삭제를 승인해 실행하려면 `--apply`를 붙인다.

```powershell
python scripts/maintain_v2_store.py cleanup --db .runtime/v2.sqlite3 --backup-dir .runtime/backups --retention-days 7 --suppliers .runtime/config/suppliers.json --apply
```

`maintenance_plan(...)`과 `apply_maintenance(...)`는 동일하게 `db_path`, `backup_dir`, `now`, `retention_days`, `revoked_source_ids`를 받는다. 적용할 때는 계획 파일을 그대로 믿지 않고 DB 쓰기 잠금 안에서 현재 스냅샷을 다시 검사한다. 계획 이후 갱신된 허용 스냅샷을 이전 해시로 삭제하지 않는다. 만료·권리 미허용·철회·보존 기한 경과·해시 손상 스냅샷을 현재 테이블에서 제거한다. 백업은 만료되었거나 보존 기한이 지났거나 철회된 공급사를 포함하면 **백업 한 쌍 전체**를 삭제한다. 복합 백업 일부를 보존하기 위해 내용과 해시를 조작하지 않는다.

## 현재 공급 계약과 유지보수 연동

실제 자료 운영에서는 세 명령 모두 `--suppliers`에 서버·수집기와 같은 설정 파일을 전달한다. 이 옵션은 설정과 증빙을 다시 읽어, 현재 관측 자료(`observed`) 중 허용 목록에 없는 공급사를 철회 대상으로 자동 포함한다. 비활성화, 조기 철회, 만료, 비교·표시·저장 권리 누락, 증빙 파일 누락·해시 불일치, 설정에서 삭제한 공급사를 반영한다. 백업·복구는 해당 자료가 있으면 거절하고, 정리는 계획에 포함한다. 현재 DB에서 이미 제거되어 백업에만 남아 있는 관측 공급사도 검사한다.

CLI는 먼저 설정을 엄격하게 검사하고, 저장소 조사 후 실행 직전에 설정·증빙을 다시 읽는다. 잘못된 JSON·스키마·필드와 읽을 수 없는 설정은 '전체 공급사 철회'로 해석하지 않고 **작업 전체를 거절하며 삭제하지 않는다**. 설정 파일은 정상이고 특정 계약 증빙만 없거나 바뀐 경우에는 해당 공급사의 사용권을 허용하지 않는다. 합성 시연 자료(`synthetic`)는 공급사 허용 목록을 요구하지 않으며, 기존 스냅샷의 권리·보존 기한과 명시적 철회는 계속 적용한다.

백업의 공급사 종류는 매니페스트 파일명·스키마·경로와 DB 체크섬을 검증한 뒤, 읽기 전용 DB 스키마 검사 및 식별자 조회로 확인한다. 검증하지 않은 JSON 경로를 DB로 열지 않는다. `--suppliers`가 있는 정리에서 백업이 손상되어 자료 종류를 안전하게 확인할 수 없으면 **삭제 전 작업 전체를 거절**한다. 해당 백업을 운영자가 확인한 뒤 다시 계획을 실행한다. 이 추가 검사가 없는 기존 정리 API의 `blocked_backups` 처리와 구분한다.

설정 파일과 SQLite 전체를 묶는 원자적 잠금은 제공하지 않는다. 계약을 변경할 때는 실행 중인 수집·백업·복구·정리를 먼저 종료하고 설정을 갱신한 뒤 다시 실행한다. CLI의 실행 직전 검사가 실행 도중 발생한 외부 파일 변경까지 원자적으로 반영한다고 가정하지 않는다. 서버의 조회 시점 계약 검사도 함께 유지한다.

`--suppliers`를 생략하면 기존 방식대로 스냅샷에 기록된 권리·만료와 `--revoke-source`만 검사한다. 이전 호출 및 격리된 시연과의 호환을 위한 동작이며, 실제 공급 계약이 있는 운영 명령에서는 생략하지 않는다. `--revoke-source`를 추가하면 현재 설정의 허용 여부와 관계없이 명시적 철회를 합쳐 적용한다. 공급사 식별자는 실제 설정값으로 바꾼다.

```powershell
python scripts/maintain_v2_store.py cleanup --db .runtime/v2.sqlite3 --backup-dir .runtime/backups --suppliers .runtime/config/suppliers.json --revoke-source 실제-source-id --apply
```

이 명령은 외부 공급사에 접속하지 않으며, 아직 로컬 설정에 반영하지 않은 철회 사건을 자동 발견하지는 않는다. **수집 설정에서도 해당 공급사를 비활성화하고 제공·수집 작업을 종료한 뒤 정리를 수행해야 한다.** 이 도구는 삭제 실행 당시의 상태를 정리하며, 이후 새로운 스냅샷 수신을 영구적으로 금지하는 권한 저장소는 아니다. 권리 만료는 별도 수동 철회 목록 없이 매번 검사한다.

삭제는 검사한 단일 DB 행과 백업 전용 디렉터리의 정확한 파일 경로에 한정한다. 재귀 삭제, 디렉터리 전체 삭제, 매니페스트가 가리키는 임의 경로 삭제를 하지 않는다. 심볼릭 링크·Windows junction·UNC·URL 경로는 거절한다. 라이브 DB를 백업 전용 디렉터리에 두는 것도 거절한다. 손상·미확인 매니페스트는 `blocked_backups`에 남겨 수동 확인을 요구한다. 확인된 스냅샷 삭제와 다른 백업 삭제를 되돌려서 만료 데이터를 복원하지 않는다. 일부 백업 실패 시 `partially_applied` 및 CLI 종료 코드 1을 반환한다.

SQLite `secure_delete=ON`을 정리에 사용하지만, SSD·파일시스템 스냅샷·WAL·외부 복사본·호스트 백업의 물리적 완전 삭제를 보장하지 않는다. 결과의 `secure_erasure_guaranteed`는 항상 `false`다. 실제 계약의 삭제 의무는 호스트 및 외부 백업 보존 정책까지 포함해 검증해야 한다.

## 운영 일정과 예산

무료 로컬 파일럿에서는 운영 전 및 종료 시 계획을 확인하고, 정리 적용 후 백업을 실행한다. 실제 운영에서 자동 정리가 필요하면 OS 스케줄러에 운영자가 동일 명령과 정확한 디렉터리를 등록한다. 이 개발 작업에서는 사용자의 컴퓨터에 반복 삭제 작업을 등록하지 않았다. 권리 만료로 조회가 막히는 것과 물리적 정리가 실행되는 시각은 다르다. 따라서 계약의 삭제 기한을 만족하는 정리 주기를 따로 정해야 한다.

암호화·원격 보관·호스트 SLA·무중단 복구는 아직 구성되지 않았다. 현재 구현은 복구 가능한 형식과 실패 시 동작을 검증한 로컬 운영 기반이다. 무료 호스팅의 임시 파일시스템에 실제 데이터를 유일하게 저장하지 않는다.

## 검증 범위

`python -m pytest backend/tests/test_v2_maintenance.py -q`로 격리된 `tmp_path`에서 확인한다. 실제 운영 DB나 사용자 백업을 테스트에서 삭제하지 않는다. 동시 import/read/backup, 복구 후 만료 차단, 철회·보존 정리, 계획의 비변경성, 조회 시점과 적용 사이 갱신, 해시 손상, 경로 탈출, 스키마 거절, 발행 실패·목적지 경합을 검증한다. Windows가 심볼릭 링크 생성을 허용하지 않으면 실제 링크 생성 테스트만 skip되며, 경로 검사 자체는 별도 모의 테스트로 검증한다.

`python -m pytest backend/tests/test_v2_maintenance_config.py backend/tests/test_v2_restore_drill.py -q`는 현재 계약에 따른 백업·복구 차단, 조기 철회·비활성화·만료 정리, 백업에만 남은 공급사 처리, 잘못된 설정의 비변경성, 실행 직전 설정 재검사, 합성 복구와 이전 CLI 호환을 확인한다. 테스트 계약은 가짜 오프라인 증빙이며, 네트워크 연결과 DNS 조회를 금지한 상태로 실행한다.
