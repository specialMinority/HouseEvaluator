# v2 implementation contract — 2026-09-13

Python standard library only for the free-first, single-instance local pilot implementation. Existing legacy code remains for offline regression. Modules are under `backend/v2/`; the UI is under `frontend/v2/`; runtime paths are not web-public. Supply, validation, access, release readiness and storage lifecycle tools are implemented. Real supplier agreements, field/city validation and operational deployment remain incomplete. See [FREE_FIRST_DEPLOYMENT.md](FREE_FIRST_DEPLOYMENT.md) and [PHASE67_VALIDATION.md](PHASE67_VALIDATION.md).

## Subject (JSON object)

`city`: tokyo/osaka/fukuoka; `municipality`: nonempty Japanese municipality; `station_id`: exact canonical ID, never substring matching; `station_name`: optional display name; `unit_id`, `building_id`: optional canonical identifiers, needed for reliable self exclusion; `layout`: 1R/1K/1DK/1LDK; `structure`: wood/light_steel/steel/rc/src or null; `property_type`: apartment (independent multi-unit dwelling only in MVP); `contract_type`: standard/fixed_term; `furnished`: boolean or null; `area_sqm`: positive finite number; `built_year`: integer or null; `walk_min`: nonnegative finite number or null; `floor`: integer or null; `orientation`: N/NE/E/SE/S/SW/W/NW or null; `bathroom_separate`: boolean or null; `rent_yen`: positive integer; `mgmt_fee_yen`: nonnegative integer or null. Additional fields rejected. Missing non-price characteristics become null if optional. Defaults property_type=apartment, contract_type=standard; furnished defaults null. `station_id`, municipality, layout, area, rent, city required. Null mgmt/structure/year/walk/bath/floor/furnished must NOT turn into zeros or inferred facts. Invalid enums/types/ranges are validation errors. Unsupported city/layout/property_type return validation errors or unsupported (documented consistently).

## Observation

Subject fields plus required `unit_id`, `building_id`, `source_id`, `listing_id`, `observation_id`; `status`: active/pending/closed/unknown; timezone-aware ISO timestamps `source_updated_at` (nullable), `received_at`, `status_verified_at` (nullable); `public_url` nullable HTTPS only. `data_kind`: observed/synthetic. IDs are canonical within the supplied dataset; cross-supplier canonicalization is the supplier/importer's explicit responsibility, not fabricated from rent. All fields are preserved. Nullable characteristic values are allowed but quality gates apply at evaluation. `unit_id` and `building_id` are nonempty for every observation.

## Source snapshot envelope

`schema_version`: "2.0"; `snapshot_id`: nonempty; `as_of`: timezone-aware ISO; `complete`: true required; `source`: {`source_id`, `independent_source_id`, `display_name`, `rights`: {`comparison`: true, `display`: true, `storage`: true, `expires_at`: ISO future}, `data_kind`: observed/synthetic}; `listings`: observation list. Source/listing IDs and data_kind must match. Empty authoritative snapshots require `allow_empty=True` at import, otherwise rejected. Old/equal/conflicting snapshot rollback must not replace newer data (same exact snapshot id/payload idempotent). Store every accepted source current snapshot atomically and expose snapshot metadata. Expired rights stop evaluation, even if import happened while valid. Validated market segments are NOT trusted from imported data or HTTP requests.

## Data APIs

`backend/v2/models.py`: `ValidationError(ValueError)`, `validate_subject(payload, *, now=None) -> dict`, `validate_observation(payload, *, now=None) -> dict`, `validate_snapshot(payload, *, now=None) -> dict`, `parse_timestamp(value) -> datetime` (UTC aware). `now` always aware UTC; no runtime dependencies.

`backend/v2/store.py`: `SnapshotStore(path)` initializes DB; `import_snapshot(payload, *, now=None, allow_empty=False, allow_synthetic=False) -> dict`; `read_current(*, now=None, include_synthetic=False) -> dict` returns {`listings`: [], `sources`: [], `snapshot_version`: str, `is_demo`: bool}; sources include source envelope metadata and snapshot_id/as_of; include only unexpired permitted sources. Synthetic and observed must never mix: include_synthetic=True reads ONLY synthetic, false ONLY observed. No real source => empty. `health(*, now=None) -> dict` counts/status only, no source secrets. DB shared across HTTP threads, per-call transactions/connections.

`backend/v2/demo.py`: `make_demo_snapshot(city, *, now=None) -> dict`, `demo_subject(city) -> dict` generates deterministic synthetic identities/characteristics/prices (24+ unique units, 12+ buildings) with conspicuous synthetic source and no real links; timestamps derived explicitly for dev simulation. Three cities. Not auto-loaded outside explicit server demo option.

CLI `scripts/import_v2_snapshot.py PATH --db PATH [--allow-empty]` with synthetic denied unless explicit `--allow-synthetic`.

## Comparison API

`backend/v2/comparison.py`: `compare(subject: dict, observations: list[dict], *, now=None, snapshot_version="", sources=None, is_demo=False, validated_segments=None) -> dict`. Calls validate_subject. `validated_segments` is server/operator-controlled set of `city/layout` strings, empty by default. Real market accuracy is unvalidated, therefore no high/low judgment absent approved segment. Synthetic always identified and cannot imply real market validation.

Returns: `assessment_id` deterministic hash of normalized subject, snapshot, policy, approved segments, mode and evaluated_at, `evaluated_at`, `status` comparable/limited/insufficient/stale/unsupported, `reason_codes`: list strings, `judgment`: higher/similar/lower or null, `is_demo`, `price_basis`: rent_plus_management, `subject_price_yen`, `benchmark_yen`, `delta_yen`, `delta_ratio`, `distribution` {q25_yen,q50_yen,q75_yen,weighting_method}, `sample` {unit_count,building_count,effective_n}, `freshness` {status_verified_at_min,status_verified_at_max}, `matching` {steps:[{step,changed_field,before,after,candidate_count}],relaxed_fields:[],missing_fields:[]}, `comparables`: [{unit_id,building_id,source_id,public_url,rent_yen,mgmt_fee_yen,total_yen,area_sqm,built_year,walk_min,structure,layout,station_id,station_name,floor,orientation,bathroom_separate,status_verified_at,differences:[str],weight}], `excluded_counts` map, `sources`: public-safe names/ids, `versions` {schema:"2.0",policy:"direct-v2.0",snapshot:snapshot_version,model:null}.

Mandatory hard gates: active status, last verified <=24h and not future, received/source date not future, same data_kind mode, positive price and known mgmt; no stale restoration. Non-missing exact station_id/city/municipality/layout/structure/type/contract/furnished/bath must agree. Exclude self canonical unit_id; if subject unit missing but building known exclude entire building conservatively; if both missing never comparable direction (identity_unverified). Dedupe canonical units; conflicting active offers are excluded rather than averaged. Same building weight total <=1. Normalize identifiers without collapsing different station IDs. If observation station is missing it is NOT exact.

Phases: strict area ±max(1sqm,5%), age±2, walk±2, orientation/floor non-special band; then orientation only relaxed, then area ±max(strict band,10%), then age±5, then walk±5 (each changes only one field; preserve structure/layout/contract/station/bath/new-build and ground/basement boundaries). Stop once >=20 units,>=10 buildings,effective_n>=12; at end limited needs >=10 units,>=5 buildings,effective_n>=8. All quantiles use same building-balanced weights; equal weights conventional median; precise method documented. Comparable only if count gates and validated segment + identity + completeness; limited judgment always null. All inadequate snapshots => benchmark/distribution values null. No price-based candidate selection, no legacy fallback. Reason policy_unvalidated always shown when not approved. New-build is age<=1, must not mix old/new. Missing critical subject conditions => insufficient rather than fabricated defaults. Fixtures/tests may use explicit validated_segments to exercise arithmetic, not market validation.

## HTTP integration

GET `/api/v2/capabilities` -> {schema_version:"2.0", cities:[{id,label}], demo_enabled:boolean, source_count:int, market_data_available:boolean, validation_status:"unvalidated"|"configured", limits:{...}}.
POST `/api/v2/evaluate` body {subject: Subject, mode:"market"|"demo"} (market default) -> comparison result. Demo forbidden unless server started with HOUSE_EVALUATOR_DEMO=1.
GET `/api/v2/demo-subject?city=tokyo` -> {subject: Subject}; only explicit demo mode.
POST `/api/v2/costs` requires integer fields {rent_yen,mgmt_fee_yen,monthly_extra_yen,stay_months,initial_payment_yen,prepaid_rent_yen,refundable_deposit_yen,exit_fee_yen,renewal_fee_yen,discount_yen}; stay_months 1..60, positive rent, other amounts >=0. Returns {monthly_base_yen,monthly_all_in_yen,upfront_cash_yen,nonrefundable_initial_yen,stay_cost_yen,deposit_at_risk_yen,average_monthly_cost_yen,stay_months,assumptions}. See OPERATIONS_V2.md for cash-flow formula; no market fetch.
GET `/api/v2/health` -> sanitized health, no paths.
Errors -> {error:code,message:Korean or precise validation string}; 400 validation,413 oversized,403 demo disabled,500 generic (no stack/path).

UI fetch paths same origin. New UI does not call legacy endpoints. Demo explicit opt-in in UI with persistent synthetic banner; no real market conclusions shown for synthetic/limited results. Render text via textContent; allow only HTTPS external links and rel=noopener noreferrer.

GET `/api/v2/stations?city=tokyo&mode=market` returns {stations:[{station_id,station_name,municipality}],city,mode}. City and mode are validated. Only current permitted matching-mode observations with active status verified in the last 24h supply this list. Demo requires the server flag. UI selects by display name/municipality; identifiers remain exact internally. No source means an empty list, never an invented station mapping.

Runtime adds `data_mode`, `validation_status`, and `receipt` to the comparison response. `receipt` contains the normalized subject, mode, approved segments, snapshot, policy, and evaluated_at. No automatic durable personal assessment history is stored. Synthetic timestamps refresh explicitly for demonstration on requests at most once per hour; real observations are never refreshed without a new permitted import.

## Operational storage and supplier contracts

`backend.v2.storage.open_store(target)` opens a persistent local SQLite file through `SnapshotStore`. It rejects memory operational storage, network/URI targets and PostgreSQL URLs; PostgreSQL/PostGIS, replication and multiple app instances are not implemented. Current complete source payloads and historical receipt hashes are stored; there is no automatic archive of every historical payload.

`backend.v2.supply.IngestionRunner(config_path, state_db, store)` uses operator-owned supplier configuration and a separate persistent SQLite work-state database. `run_once()` executes due work; `monitor_status(state_db, *, now=None)` returns sanitized state. `scripts/run_v2_ingestion.py --config PATH --db PATH --state-db PATH --once` performs one bounded pass. `--worker` explicitly keeps running; `--status` reads status. No scheduler or external notification account is installed automatically.

Configured inputs are local normalized JSON files or exact-origin permitted HTTPS JSON feeds. Contracts pin agreement content with SHA256 and explicit permissions, expiry and revocation. No website scraper, redirect following or provider-specific policy bypass is supplied. Durable leases, retries, resume state and fixed error codes survive restarts. HTTP 304 and unchanged snapshots never refresh observation timestamps.

`Runtime.market_data(now=...)` checks configured supplier permissions again on every read. The server must receive `HOUSE_EVALUATOR_SUPPLIERS` and the worker's state path through `HOUSE_EVALUATOR_INGESTION_STATE`. Revocation, disabled sources, expired contracts, missing/changed evidence or invalid configuration exclude stored observations. Development mode without supplier configuration checks snapshot rights only; running a worker does not automatically configure another server. Pilot mode requires supplier configuration.

## Market evidence and approval

`backend.v2.validation.validate_market(manifest, *, base_dir, smoke=False)` returns deterministic evidence from local versioned snapshots, explicit availability/evaluation timestamps, chronological holdouts and global held-out building exclusion. It never updates the approval registry. `render_markdown(report)` produces its readable companion. CLI `scripts/validate_v2_market.py MANIFEST --output REPORT.json` also writes a Markdown file; exit 0 means an eligible market segment exists, 3 means evidence failed gates, 2 means invalid input. Explicit `--smoke` may exit 0 for a completed synthetic software exercise but eligibility remains false.

Report schema is `market-validation-1.0`, with `report_kind`, `generated_at`, `policy_version`, `policy_sha256`, exact `source_ids`, input hashes, fixed thresholds, split, supply evidence, segment metrics/gates and request results. Advertised rents are surrogate outcomes, not fair-rent ground truth. Market reports reject synthetic data. See [MARKET_VALIDATION_V2.md](MARKET_VALIDATION_V2.md) for the full manifest, minimum sample and review contracts.

`backend.v2.approval.approved_segments(registry_path, source_ids, now)` requires registry schema `2.0`; entries have `policy_version`, `approved:true`, nonempty `approved_by`, exact `source_ids`, requested `segments`, aware `validated_at`/`expires_at`, relative `report_path` and `report_sha256`. Reports must remain inside the registry directory, be JSON, match the pinned byte hash and current `comparison.py` SHA256, identify market data and the exact active source set, and be no older than 30 days. Report generation cannot follow approval time. Registry/report size is at most 2,000,000 bytes each.

Top-level eligibility and each requested segment eligibility must be true. All 23 required market gates must exist and every reported gate must be boolean true; absent/false/numeric values fail. The operator still verifies rights, genuine observations, expert-review integrity and the appropriateness of published scope. A source/client cannot approve its own segment. The example registry ships with no approved segments.

Use a layout such as `.runtime/config/registry.json`, `.runtime/config/release.json` and `.runtime/config/reports/*.json`, so each registry's relative `reports/...` path remains within its directory. Generated reports are not registered automatically.

## Access and current-server readiness

`AccessPolicy` optionally requires an ASCII, no-whitespace 32..256 character Bearer token for all `/api/` routes. Static UI remains available for access-code entry. The UI keeps the token in memory only. API rate limiting uses the directly connected IP, never user-supplied forwarding headers; default is 120 requests/minute, configured range 1..10000, and tracked clients are bounded. These are process-local controls for one instance.

HTTP adds 401 access-required and 429 rate-limited responses, with `Retry-After: 60` on 429. It uses 16 request slots and an absolute 10-second connection deadline covering slow headers/bodies as well as the socket read timeout. Request body limit is 65,536 bytes. The deadline may close the connection without a JSON response. Unsupported content type returns 415; malformed framing/JSON returns 400; capacity exhaustion returns 503. Request logs omit raw URL/query values and tokens.

`GET /api/v2/supply-status` returns sanitized ingestion status. `GET /api/v2/readiness` evaluates this running server and returns schema `release-readiness-1.0`, `ready`, `checks`, `blockers`, `eligible_segments`, `segment_availability`, `source_ids`, `context_fingerprint`, scope `single_instance_private_pilot` and budget 0 yen/month. Status is 200 when ready, otherwise 503. Both endpoints require authentication when configured.

`HOUSE_EVALUATOR_PILOT=1` requires an access code and supplier configuration at startup, with demo/legacy disabled. Every evaluation then rechecks readiness; missing release evidence produces 503 `release_not_ready`. Development mode is not automatically protected by this release gate.

Readiness requires permitted actual data and approved segments, successful non-overdue workers, access protection, demo/legacy disabled, restore/load/alerts/usability evidence, a named budget confirmation for exactly integer 0 monthly cost and explicit operator release approval. Every approved segment must currently have at least 20 unique fresh active units across 10 buildings with known critical fields. This is a release inventory gate; the comparison engine separately checks each request's actual matching and effective sample size.

Release evidence registry schema is `release-evidence-1.0`; `reports[kind]` references `{path,sha256}` within its directory. Each report must match kind, hash, `passed:true`, `scope:market_operations` and the current context fingerprint. Operational reports are valid for at most 7 days; usability review for 30 days. Fingerprinting covers all v2 Python modules, the server, v2 JS/HTML/CSS, supplier configuration and source set. Synthetic demonstrations cannot satisfy these gates.

Load evidence additionally requires `workload:evaluate_market`, at least 60 requests, concurrency 4, 10 distinct target units across 5 buildings and reference prices in at least 95% of responses. The current loopback measurement CLI passes on all HTTP 200 responses and P95 <=5 seconds; this is a prototype threshold, distinct from the plan's 3-second goal and from Internet/multi-instance capacity.

`scripts/check_v2_release.py` is a **local configuration preflight**, constructing a new `Runtime(demo_enabled=False)` from specified files and checking the selected token environment variable. It does not inspect a running/remote server or its demo/legacy environment variables. It does not deploy or approve. For actual running configuration use that server's readiness API. CLI exit codes: ready 0, unmet gates 2, execution error 1.

## Backup, retention and drill APIs

`backend.v2.maintenance` provides `backup_store(db_path, backup_dir, *, now=None, retention_days=7, revoked_source_ids=())`, `restore_backup(manifest_path, destination, *, now=None, revoked_source_ids=())`, `maintenance_plan(...)` and `apply_maintenance(...)`. Backup uses SQLite's online backup API, a managed fresh file pair and a checksum/expiry manifest. Restore validates schema, checksum and rights into a fresh destination only; it never overwrites a live database.

`scripts/maintain_v2_store.py` exposes `backup`, `restore`, `cleanup`. Cleanup defaults to a read-only plan; `--apply` explicitly removes eligible current source rows and exact managed backup pairs. Receipts remain to prevent deleted snapshots from being resurrected by reimport. Default 7-day retention is an implementation assumption, not a supplied contractual right. Physical secure erasure, remote copies and disk-failure protection are not guaranteed.

Phase 7.3 adds `--suppliers` to backup, cleanup and restore. With it, the CLI checks current contracts, intersects observed source inventories with permitted sources, unions explicit `--revoke-source` values, and rejects malformed settings before any deletion. Without it, early revocation must still be supplied explicitly via `--revoke-source`; snapshot-embedded rights expiry is always checked. Contract changes and maintenance should not run concurrently because there is no atomic multi-file configuration lock. No OS cleanup schedule is registered.

`scripts/drill_v2_restore.py` performs backup and restoration into a disposable directory and compares snapshot/receipt hashes and counts, without replacing the live DB. It creates an unregistered operations report; a market scope requires permitted actual sources and no synthetic rows. Backup manifests/drill/load reports contain hashes and aggregate metadata, not user assessment input. Market validation reports, in contrast, retain target unit/building IDs, station and prices and are internal evidence, not anonymous public outputs.

See [STORAGE_LIFECYCLE_V2.md](STORAGE_LIFECYCLE_V2.md) for scoped deletion and partial failures. The Phase 6~7 baseline had 356 passed, 1 skipped, 61 subtests; its historical record is [PHASE67_VALIDATION.md](PHASE67_VALIDATION.md). Phase 7.3 subsequently exercised the real Docker image, restart persistence, synthetic restore and local incident drills. Latest results are in [DEVELOPMENT_PHASES.md](../DEVELOPMENT_PHASES.md); actual market deployment remains incomplete.

`GET /healthz` returns only `200 {"status":"ok"}` without authentication, rate-budget consumption, storage reads or market readiness checks. It supports HEAD and is intended for local/container liveness. It does not prove market availability. The optional public proxy hides this route. Readiness remains authenticated and returns 503 until the real release gates pass.

`scripts/rehearse_v2_pilot.py --output-dir FRESH_PATH` creates its own local Docker project, image, empty configuration and synthetic data volumes, tests abrupt restart/recreation and release blocking, then removes only those temporary resources. Its report schema is `deployment-rehearsal-1.0`, scope `synthetic_smoke`, and it never registers release approval. `check_v2_alerts.py` and `drill_v2_alerts.py` persist/verify local incident transitions only; [ALERTS_V2.md](ALERTS_V2.md) documents their read-only source inspection and separate journal.
